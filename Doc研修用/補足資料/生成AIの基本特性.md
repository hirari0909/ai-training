# 🤖 生成AIの基本特性

> **本資料の目的**
> 生成AIを業務で活用するうえで知っておくべき**基本的な仕組みと挙動**をまとめた資料です。
> 「なぜそう動くのか」を理解することで、より効果的にAIを使いこなせるようになります。

---

## 📌 1. 生成AIの基本的な挙動

### 1-1. 「学習させる」はできない

| よくある誤解 | 実際の挙動 |
|:---|:---|
| 「AIに教えれば覚えてくれる」 | 利用者がモデル自体を学習させる機能は**存在しない** |
| 「使い続ければ賢くなる」 | モデルの知識は**学習済みデータで固定**されている |

- 生成AIのモデルは、提供元（OpenAI、Google、Anthropicなど）が**事前に大量のデータで訓練**したものです
- 利用者が会話を通じてモデルの知識を更新・追加することは**できません**
- 会話中に「覚えて」と言っても、それはそのセッション内でのみ有効であり、モデル自体は変化しません

> [!NOTE]
> **Fine-tuning（ファインチューニング）** や **RAG（検索拡張生成）** といった技術を使えば、特定の知識を活用させることは可能ですが、これは通常の利用者が行う操作ではなく、開発者・管理者レベルの作業です。

---

### 1-2. 要求は「プロンプト」で行う

生成AIへの指示・質問はすべて **プロンプト（Prompt）** と呼ばれるテキストで行います。

```
┌─────────────────────────────────┐
│  プロンプト（入力）               │
│  「○○について教えてください」     │
└──────────────┬──────────────────┘
               ▼
        ┌──────────────┐
        │  生成AIモデル  │
        └──────┬───────┘
               ▼
┌─────────────────────────────────┐
│  レスポンス（出力）               │
│  「○○とは、～～です。」          │
└─────────────────────────────────┘
```

#### 💡 プロンプトの質 ＝ 応答の質

プロンプトの書き方によって、AIの応答品質は**大きく変わります**。

| プロンプトの例 | 品質 | 理由 |
|:---|:---:|:---|
| `「なんか教えて」` | ❌ 低い | 曖昧すぎてAIが意図を特定できない |
| `「Javaのインターフェースについて教えて」` | ⭕ 普通 | トピックは明確だが、深さ・形式が不明 |
| `「Javaのインターフェースについて、初心者向けに、具体的なコード例を含めて説明してください」` | ✅ 高い | 対象・レベル・形式が明確 |

> [!TIP]
> **良いプロンプトの要素：**
> - **役割の指定**：「あなたはJavaの講師です」
> - **具体的な指示**：何を、どのように、どの程度
> - **出力形式の指定**：「箇条書きで」「表形式で」「コード付きで」
> - **制約条件**：「200文字以内で」「専門用語は避けて」

---

### 1-3. 通信はステートレスである

生成AIとのやり取りは、**ステートレス（Stateless）** な通信です。

#### ステートレスとは？

```
【ステートレス（生成AI）】
  リクエスト1 → レスポンス1   ※これで完結。AIは何も覚えていない
  リクエスト2 → レスポンス2   ※リクエスト1の内容は知らない

【ステートフル（一般的なWebアプリ）】
  リクエスト1 → レスポンス1   ※サーバーがセッションに状態を保存
  リクエスト2 → レスポンス2   ※セッションから前回の状態を参照できる
```

| | ステートレス | ステートフル |
|:---|:---|:---|
| **状態の保持** | サーバー側で保持しない | サーバー側で保持する |
| **代表例** | 生成AI API、REST API | Webアプリのログインセッション |
| **通信の単位** | 1リクエスト → 1レスポンスで完結 | 複数リクエストにまたがって状態を維持 |

> **技術的補足：** 生成AIのAPI呼び出しは `HTTP Request → HTTP Response` の1往復で完結します。前回のやり取りを「覚えている」のはAI側ではなく、**クライアント側の仕組み**です。

---

### 1-4. なぜ「会話」ができるのか？

ステートレスなのに会話が成立する理由——それは**クライアント側が過去の履歴をプロンプトに含めて送信している**からです。

```
【1回目のやり取り】
  送信: 「Javaとは何ですか？」
  応答: 「Javaとはプログラミング言語です。」

【2回目のやり取り（実際に送信される内容）】
  送信: 「ユーザー: Javaとは何ですか？
         AI: Javaとはプログラミング言語です。
         ユーザー: その特徴を教えてください」  ← 履歴 + 新しい質問
  応答: 「Javaの特徴は、オブジェクト指向で…」
```

> [!IMPORTANT]
> AIが「前の会話を覚えている」ように見えるのは、**毎回すべての会話履歴を送り直している**からです。AI自身が記憶しているわけではありません。

## 📌 2. AI Chatにおける「セッション」

### 2-1. セッションの概念

AI Chatにおける **セッション** とは、1つの会話スレッド（やり取りの単位）を指します。

```
セッションA（話題：Java研修）        セッションB（話題：設計レビュー）
┌──────────────────────┐          ┌──────────────────────┐
│ Q: Javaとは？          │          │ Q: ER図の書き方は？    │
│ A: プログラミング言語…  │          │ A: エンティティを…     │
│ Q: 特徴は？            │          │ Q: 正規化とは？       │
│ A: オブジェクト指向で…  │          │ A: データの冗長性を…   │
│ Q: 例を見せて          │          │        ：             │
│        ：              │          └──────────────────────┘
└──────────────────────┘
※ セッションAとBは完全に独立。互いの内容は参照できない
```

---

### 2-2. セッションが長くなると起きる問題

セッションを使い続けると、会話履歴が蓄積されていきます。これには**3つの問題**があります。

#### ⚠️ 問題① コンテキストウィンドウの上限

| 項目 | 説明 |
|:---|:---|
| **問題** | 履歴が長くなりすぎると、AIが処理できる入力サイズ（**コンテキストウィンドウ**）を超える |
| **結果** | 古い会話が切り捨てられたり、エラーが発生する |
| **対策** | 話題が変わったら**新しいセッション**を開始する |

> **コンテキストウィンドウとは：** AIが一度に処理できるテキスト量の上限。モデルによって異なり、例えばGPT-4oは128Kトークン、Claude Opusは200Kトークンなど。

#### ⚠️ 問題② トピック混在による精度低下

| 項目 | 説明 |
|:---|:---|
| **問題** | 1つのセッションに**複数の話題**が混在すると、AIの応答精度が下がる |
| **原因** | AIはプロンプト全体を文脈として解釈するため、無関係な話題がノイズになる |
| **対策** | **1セッション = 1トピック**を意識する |

#### ⚠️ 問題③ コストの増加

| 項目 | 説明 |
|:---|:---|
| **問題** | 履歴が長くなるほど、毎回送信するデータ量が増え、**利用コストが増加**する |
| **仕組み** | API利用料金は送受信した**トークン数**に基づいて課金される |
| **対策** | 不要になったセッションは閉じ、こまめに新しいセッションを開始する |

> [!NOTE]
> **トークンとは：** AIが文章を処理する際の最小単位。日本語の場合、1文字が1〜3トークン程度に相当します。「こんにちは」は約5トークンです。

## 📌 3. 生成AIの出力特性

AIを正しく活用するためには、その**出力の性質**を理解しておくことが重要です。

### 3-1. 確率的な応答（同じ入力でも結果が変わる）

生成AIは、次に来るべき単語を**確率的に選択**して文章を生成します。そのため、**同じプロンプトでも毎回異なる応答**が返ることがあります。

```
同じプロンプト「Javaの特徴を3つ教えて」

  1回目の応答: ① オブジェクト指向 ② プラットフォーム非依存 ③ ガベージコレクション
  2回目の応答: ① 静的型付け ② マルチスレッド ③ 豊富なライブラリ
```

> この性質は**temperature（温度）** というパラメータで制御できます。温度が低いほど決定的（毎回同じ）な応答になり、高いほど創造的（ばらつきのある）応答になります。

---

### 3-2. ハルシネーション（もっともらしい嘘）

生成AIは、**事実と異なる内容をあたかも正しいかのように出力する**ことがあります。これを **ハルシネーション（Hallucination：幻覚）** と呼びます。

| 特徴 | 説明 |
|:---|:---|
| **なぜ起きる** | AIは「確率的にもっともらしい文章」を生成しているだけで、事実を検証していない |
| **どんな時に多い** | 学習データに含まれていない情報、最新の情報、ニッチな専門知識 |
| **対策** | 重要な情報は必ず**一次情報源で裏取り**する。AIの出力を鵜呑みにしない |

> [!WARNING]
> **業務でAIを活用する際の鉄則：**
> AIの出力は「下書き」や「たたき台」として扱い、**最終的な判断・確認は必ず人間が行う**こと。

---

### 3-3. 学習データの知識の範囲（カットオフ）

生成AIの知識には**期限**があります。これを **ナレッジカットオフ（Knowledge Cutoff）** と呼びます。

- モデルは学習時点までのデータしか持っていません
- カットオフ以降に起きた出来事や変更された情報については、**正確に回答できない**可能性があります
- 最新情報が必要な場合は、**Web検索機能付きのAI**や**RAG**の活用を検討してください

## 📌 4. 効果的なAI活用のためのベストプラクティス

| # | プラクティス | 説明 |
|:---:|:---|:---|
| 1 | **1セッション1トピック** | 話題が変わったら新しいセッションを開始する |
| 2 | **プロンプトは具体的に** | 役割・条件・出力形式を明示する |
| 3 | **出力は必ず検証する** | ハルシネーションの可能性を常に意識する |
| 4 | **長いセッションは避ける** | コスト・精度の両面でデメリットがある |
| 5 | **段階的に質問する** | 一度に多くを求めず、ステップバイステップで深掘りする |
| 6 | **出力形式を指定する** | 「表で」「コード付きで」「箇条書きで」など形式を明示する |
