# 結合テスト用データを作成する

「01.ケース作成」で起こした各シナリオ／ケースの**事前準備・前提条件**を満たす、決定論的なテストデータを設計し、H2へ投入できる形（`data.sql`）で作成する。

## 前提（対象アプリ／投入方式）
- **対象**: `training-bookshelf`（書籍管理システム）
- **DB**: H2 インメモリ（`jdbc:h2:mem:testdb`）
- **投入方式**: Spring Boot の SQL 初期化機能
  - `application.properties` に `spring.sql.init.mode=always` 設定済み
  - アプリ起動毎に `src/main/resources/schema.sql`（DROP+CREATE）→ `src/main/resources/data.sql` が自動実行される
  - インメモリDBのため**再起動の度に初期化される＝冪等**。テスト再実施前にアプリを再起動すれば毎回同じ初期状態になる
- **作成対象ファイル**: `training-bookshelf/src/main/resources/data.sql`
  - 既存の `data.sql` にはデモ用の書籍50件が入っている。結合テストでは期待結果を固定するため、**ケース前提に合わせた決定論的データで置き換える**（元データはgit履歴で復元可能）

---

## 1. データを設計する

### 入力（ケースを正とする）
| 用途 | パス |
|------|------|
| データ前提の抽出（最重要）| `Docsシステム/結合テスト/ケース/00_テストケース一覧.md` と各 `SCxx_*.md` の「事前準備」「前提条件」 |
| カラム定義・制約の確認 | `training-bookshelf/src/main/resources/schema.sql`、`Docsシステム/外部設計/04TBL定義.md` |
| マスタ値の確認 | `Docsシステム/外部設計/05個別画面設計/05個別画面設計_BK01_書籍一覧画面.md`（カテゴリ選択肢）、`03ER図.md` |

### 設計手順
1. 全シナリオ詳細の「事前準備」「前提条件」を洗い出し、**必要なデータ要件**を一覧化する
2. 1つの `data.sql` で**全シナリオの前提を同時に満たす**ように、共有データセットを設計する（シナリオ毎に別データにしない）
3. 期待結果と突き合わせられるよう、**book_id 等のキーを明示的に固定**して採番する

### 必ず用意するデータ要件（ケースから漏れやすい観点）
- **カテゴリマスタ**: BK01 のカテゴリ選択肢（categories 全9件、category_id 1〜9・名称は画面設計通り）
- **基本書籍**: 一覧・詳細・編集・削除の対象となる、IDが既知の書籍を数件
- **ページング用件数**: SC06 のページング検証用に、最終ページ・端数が出る件数（例: 1ページ20件 → 41件で3ページ）
- **検索ヒット用**: タイトル／著者の部分一致、カテゴリ完全一致が検証できる組み合わせ
- **レビュー有無**: 平均評価・レビュー数の集計検証用に「レビューあり書籍」「レビュー0件書籍」の双方
- **ISBN重複検証用**: 登録バリデーション（`validation.duplicate.isbn`）を発火させる既知ISBNの書籍
- **桁数境界**: タイトル100桁ちょうど等、境界値ケースの対象データ（必要な場合）
- **削除連動確認用**: レビューを持つ書籍（削除時の reviews CASCADE 確認）
- **楽観ロック検証用**: 編集競合ケースがある場合、対象書籍の `updated_at` を既知値で固定

## 2. data.sql を作成する

### 出力先
- `training-bookshelf/src/main/resources/data.sql`（既存を置換）

### 作成ルール
- **文字コードは UTF-8**（`spring.sql.init.encoding=UTF-8`）。日本語データを含めてよい
- **INSERT順序は FK 依存順**: `categories` → `books` → `reviews`
- **キーは明示指定**して固定する（`INSERT INTO books (book_id, ...) VALUES (1, ...)`）。期待結果（URL の `/book/detail/{bookId}` 等）と一致させるため、AUTO_INCREMENT 任せにしない
- schema.sql の制約を必ず満たす
  - `books.isbn` は UNIQUE（重複検証用を除き重複させない）
  - `books.price >= 0`（CHECK）
  - `reviews.rating` は 1〜5（CHECK）
  - `books.category_id` は categories に存在する値（FK）
  - NOT NULL カラム（title/author/publisher/published_date/isbn/category_id/price）は必ず値を入れる
- `created_at` / `updated_at` は、楽観ロック・並び順検証で必要な場合のみ明示値を入れる（不要なら DEFAULT に任せる）
- 既存 `data.sql` 冒頭の `sample` テーブル用 INSERT は schema.sql に `sample` 定義がある間は残す（削除しない）
- 各データブロックの先頭に、**どのシナリオ／ケースの前提を満たすためのデータか**をコメントで明記する
  ```sql
  -- [SC06] ページング検証用: books を計41件投入し3ページ構成にする
  -- [SC01] ISBN重複バリデーション用: isbn=9784873115658 を既存登録済みにする
  ```

## 3. データ定義書を出力する

投入データの意図をテスト実施者が追えるよう、定義書を作成する。

### 出力先・ファイル名
- `Docsシステム/結合テスト/データ/データ定義書.md`

### テンプレート（必須セクション）
```markdown
# 結合テスト用データ定義書

## 1. 投入方式
H2インメモリ。`schema.sql`→`data.sql`がアプリ起動毎に実行され初期化される（冪等）。

## 2. categories
| category_id | category_name |
|-------------|---------------|
| 1 | 小説・文学 |

## 3. books
| book_id | title | author | category_id | isbn | レビュー | 用途（対応シナリオ・ケース）|
|---------|-------|--------|-------------|------|---------|----------------------------|
| 1 | ... | ... | 3 | ... | あり3件 | SC04 閲覧, SC02 編集対象 |

## 4. reviews
| review_id | book_id | reviewer_name | rating | 用途 |

|----------|---------|---------------|
```

## 4. 投入を確認する

1. アプリを起動する: `mvn -pl training-bookshelf spring-boot:run`（または既存の起動手順）
2. 起動ログで `schema.sql` / `data.sql` 実行時にエラーが出ていないことを確認する
3. H2 コンソール（`/h2-console`, JDBC URL `jdbc:h2:mem:testdb`, user `sa`）で件数・キーを確認する
   ```sql
   SELECT COUNT(*) FROM books;     -- 期待件数と一致するか
   SELECT COUNT(*) FROM reviews;
   SELECT * FROM books WHERE book_id = 1;  -- 既知IDが意図通りか
   ```
4. BK01（`/book/list`）を開き、件数・ページ数・カテゴリ選択肢が前提通り表示されることを確認する

---

## 5. 作成時の注意
- **冪等性**: 再テスト時はアプリ再起動で初期状態に戻る。SQLは何度流しても同結果になるよう、明示IDで重複INSERTにならない構成にする
- **ケースとの整合**: データ変更時は「01.ケース作成」の事前準備・期待結果と必ず突き合わせ、齟齬があればケース側と同期する
- **設計書を正とする**: カテゴリ名・カラム制約は外部設計／schema.sql に従う。実装都合でデータを歪めない
- 投入失敗の典型原因（FK違反・ISBN重複・CHECK違反・NOT NULL欠落・文字コード）を投入前にセルフチェックする
- 既存デモデータを置き換える点をデータ定義書冒頭に明記する（レビュー時の認識齟齬防止）
