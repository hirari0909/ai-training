# 結合テストケースを作成する

シナリオ（画面フロー）軸で、**手動テスト手順書**形式の結合テストケースを作成する。

## 前提（対象アプリ）
- **対象**: `training-bookshelf`（書籍管理システム）
- **バックエンド**: Spring Boot 3.5.8 (Java 21) / Thymeleaf / MyBatis
- **DB**: H2（開発）／MySQL 8.x（本番）
- **テスト種別**: 結合テスト（画面〜DBを通した一連の動作確認）
- **実行形態**: 人が画面を操作して実施する**手動テスト手順書**

---

## 1. ケースを作成する

### 入力（設計書を正とする）
| 用途 | パス |
|------|------|
| 全体フローの把握 | `Docsシステム/外部設計/02画面遷移図.md` |
| 各画面の項目・処理・遷移 | `Docsシステム/外部設計/05個別画面設計/` 配下の MD（BK01〜BK13）|
| 期待メッセージの確認 | `Docsシステム/外部設計/06メッセージ一覧.md` |
| データ前提条件の確認 | `Docsシステム/外部設計/03ER図.md`、`04TBL定義.md` |
| 画面イメージの参照（任意）| `Docsシステム/外部設計/05個別画面設計/img/`、`html/` |

### 作成手順
1. **全体フローを理解する**
   `02画面遷移図.md` を読み、画面一覧・遷移・主要フロー（第3章）・セッション管理（第4章）・パラメータ受け渡し（第5章）・エラー時遷移（第6章）を把握する。
2. **画面設計を読み込む**
   フローに登場する各画面の `05個別画面設計_BKxx_*.md` を読み、画面項目定義・処理機能定義（INPUT/処理/OUTPUT）・バリデーション・メッセージ・エラーハンドリングを把握する。
3. **シナリオ・ケースを起こす**
   下記の**シナリオ単位**でテストケースを作成する。各シナリオは「画面をまたぐ一連の操作」を1本の手順として記述し、観点ごとにケースを分岐させる。

### シナリオ一覧（02画面遷移図 第3章に対応）
| シナリオID | シナリオ名 | 主なフロー |
|-----------|-----------|-----------|
| SC01 | 書籍登録フロー | BK01 → BK03 → BK04 → BK05 → BK01/BK02 |
| SC02 | 書籍編集フロー | BK01/BK02 → BK06 → BK07 → BK08 → BK01/BK02 |
| SC03 | 書籍削除フロー | BK01/BK02 → BK09 → BK10 → BK01 |
| SC04 | 書籍閲覧フロー | BK01 → BK02 → BK01 |
| SC05 | レビュー投稿フロー | BK02 → BK11 → BK12 → BK13 → BK02 |
| SC06 | 一覧画面の検索・ソート・ページング | BK01 単画面（フローを補完する観点）|

### 観点の網羅（各シナリオで最低限カバーする）
- **正常系（基本フロー）**: 入力→確認→完了まで通し、各画面の表示項目・遷移・完了メッセージ・DB反映を確認
- **確認画面からの戻り**: 確認→入力に戻った際の入力値保持（セッション保持／復元）
- **キャンセル**: キャンセル押下時の遷移先とセッションクリア
- **異常系**: バリデーションエラー（必須・桁数・形式・範囲・重複）で入力画面に留まりエラーメッセージ表示／入力値保持、データ不存在、楽観ロック失敗、DBエラー時のシステムエラー画面
- **境界値**: 桁数の上下限、0/null/空文字、ページ最終ページ・端数、評価1〜5の境界
- **メッセージ照合**: 表示文言は `06メッセージ一覧.md` のメッセージIDと本文に一致すること

---

## 2. テストケース一覧を作成する

シナリオ詳細を起こす前（または起こした直後）に、全ケースを横断管理する**テストケース一覧**を作成する。これはテスト実施・進捗管理のマスター表であり、シナリオ詳細ファイルと1対1で対応させる。

### 出力先・ファイル名
- ファイル: `Docsシステム/結合テスト/ケース/00_テストケース一覧.md`

### 作成ルール
- シナリオ一覧（SC01〜SC06）と、各シナリオで洗い出した全ケースを**1ケース1行**で列挙する
- ケースNo・観点・対象画面はシナリオ詳細と完全に一致させる（齟齬があれば詳細側を正として一覧を直す）
- 実施結果・実施日・実施者・備考の列を設け、テスト実施時に記入できる空欄で用意する
- 観点区分は `正常系 / 異常系 / 境界値 / セッション / メッセージ` から付与する
- 優先度は `高（基本フロー）/ 中（異常・境界）/ 低（補完観点）` の目安で付与する

### テストケース一覧テンプレート（必須セクション）
```markdown
# 結合テストケース一覧

## 1. シナリオ索引
| シナリオID | シナリオ名 | 対象フロー | 詳細ファイル | ケース数 |
|-----------|-----------|-----------|-------------|---------|
| SC01 | 書籍登録フロー | BK01→BK03→BK04→BK05→BK01/BK02 | [SC01_書籍登録フロー.md](SC01_書籍登録フロー.md) | n |

## 2. ケース一覧
| ケースNo | シナリオ | ケース名 | 観点 | 対象画面 | 優先度 | 実施結果 | 実施日 | 実施者 | 備考 |
|----------|---------|---------|------|---------|--------|---------|--------|--------|------|
| SC01-001 | 書籍登録フロー | 正常登録（一覧→入力→確認→完了） | 正常系 | BK01,BK03,BK04,BK05 | 高 | | | | |
| SC01-002 | 書籍登録フロー | 確認画面から戻り入力値保持 | セッション | BK03,BK04 | 中 | | | | |
| SC01-003 | 書籍登録フロー | 必須項目未入力でバリデーションエラー | 異常系 | BK03 | 中 | | | | |

## 3. 集計
| 項目 | 値 |
|------|-----|
| 総ケース数 | n |
| 観点別（正常/異常/境界/セッション/メッセージ）| - / - / - / - / - |
| 実施結果（OK/NG/未実施）| - / - / - |
```

### 整合性ルール
- 一覧の総ケース数 ＝ 全シナリオ詳細ファイルのケース数の合計
- ケースNoは一覧・詳細で重複・欠番がないこと（採番ルールは「4. ケースNo採番ルール」に従う）

---

## 3. 出力

### 出力先・ファイル名
- 配置先: `Docsシステム/結合テスト/ケース/`
- テストケース一覧: `Docsシステム/結合テスト/ケース/00_テストケース一覧.md`（「2.」で作成）
- シナリオ詳細: `{シナリオID}_{シナリオ名}.md`（例: `SC01_書籍登録フロー.md`）

### ケース仕様書テンプレート（必須セクション）
```markdown
# 結合テストケース: {シナリオID} {シナリオ名}

## 対象フロー
{画面遷移}（例: BK01 → BK03 → BK04 → BK05 → BK01）
**設計書参照**: 02画面遷移図.md 3.x、05個別画面設計_BKxx〜BKxx

## 事前準備（共通）
| 項目 | 内容 |
|------|------|
| 起動 | アプリ起動・トップ（BK01）表示 |
| データ前提 | （例）categories 全件登録済み、books に既知の3件 |
| 環境 | H2（初期データ投入済み）|

---

## {ケースNo}: {ケース名}（観点: 正常系/異常系/境界値/...）
**前提条件**: {このケース固有の前提}

| 手順No | 操作 | 入力値 | 期待結果（画面表示／メッセージ／遷移／DB） |
|--------|------|--------|------------------------------------------|
| 1 | BK01でタイトルに「xxx」入力し新規登録ボタン押下 | title=... | BK03へ遷移。入力フォームが空表示 |
| 2 | 必須項目を入力し確認画面へ押下 | ... | BK04へ遷移。入力内容が確認表示される |
| 3 | 登録ボタン押下 | - | BK05へ遷移。`bk05.message.success` 表示。books に1件INSERT |

**事後確認**: セッションの入力データがクリアされていること
```

---

## 4. ケースNo採番ルール
- 形式: `{シナリオID}-{連番3桁}`（例: `SC01-001`, `SC01-002`）
- 1ケース＝1観点を原則とし、観点をケース名に明記する

---

## 5. 作成時の注意
- 設計書と実装に乖離がある場合は**設計書を正**としてケースを作る（実装の疑義は備考に残す）
- 期待結果は「画面表示・メッセージ・遷移先・DB状態」を具体的な値で書く（"正常に動作する" のような曖昧表現は禁止）
- メッセージはメッセージIDと本文の両方を期待結果に記載する
- セッション保持／クリアのタイミングは `02画面遷移図.md` 4章に従って必ず確認ケースを設ける
- 既存参考: `Docsシステム/単体テスト/仕様書/` のケース表記法（No・前提・入力・期待結果）に倣う
